## 1. 文档说明与需求编号规则

### 1.1 交付层级（代替排期）

本文档不设里程碑与时间计划，用**交付层级**表达需求的重要性，供排期时参考：

| 层级 | 含义 | 判断标准 |
|---|---|---|
| **L1 基线** | 平台最小可用闭环，缺一则主链路不通 | 卖→交付→激活→监控→运维 这条链上的所有需求 |
| **L2 增强** | 完整商业体验，基线跑通后应尽快补齐 | 多渠道支付、报表、多端覆盖、经销商体系等 |
| **L3 扩展** | 增值业务，按业务节奏独立启用 | 租赁、订阅、梯次/回收、保险、融资租赁等 |

> 原项目实际交付顺序（M0 基建→P0 主数据→P1 交易→P2 资产/IoT→P3 运维→P4 分析→P5 多端→P6 增值）可作为排期参考，但不是本需求文档的一部分。

### 1.2 编号规则

- 非功能需求：`NFR-<类代码>-<序号>`

## 2. 项目定位与业务模式

### 2.1 业务定位

以电池设备为核心资产的**全生命周期管理平台**，覆盖"卖电池 → 装电池 → 修电池 → 再利用"全链路。一套系统支撑四种商业模式：

| 模式 | 内容 | 关键差异 |
|---|---|---|
| **A · 售卖场站** | 储能电站/充电站/换电站等"多设备组合"销售 | 场站级合同 + 场站级质保 + 告警聚合 + 驻场人员；下单后自动建站 |
| **B · 售卖设备** | 单台电池包/充电桩销售 | 设备级质保；扫码激活绑定客户 |
| **C · 设备租赁** | 以租代售：月/季/年租合同 + 押金托管 + 到期归还/买断 | 设备 RENTED 状态、租金计划、逾期罚息、归还验收工单 |
| **D · BaaS 订阅** | 电池按月订阅（含换电/充电额度），按月付费 | 独立订阅域：计划/实例/周期账单；第一阶段 JSAPI 主动支付 |

核心价值链：**商品 → 订单 → 库存 → 合同/质保 → 设备激活 → 监控告警 → 工单运维 → 分析报表**。

### 2.2 范围内（In Scope）

- **商业域**：商品、价格、库存、订单、物流、财务（支付/退款/发票/对账/押金/返利）
- **合同质保域**：合同、电子签署（存证型起步，第三方 CA 可插拔）、质保、延保、SLA、索赔、租赁条款
- **资产域**：设备主数据、激活、生命周期（含租赁/退役）、IoT 遥测、指令下行、OTA、场站
- **运维域**：告警、工单、巡检、SLA 计时
- **分析域**：六大报表、指标字典、异步导出、BI 自助查询、数仓 ETL、业务对账
- **增值域**：租赁管理、BaaS 订阅、梯次利用（退役评估/二次销售）、回收管理、商城、经销商返利
- **平台能力**：身份认证、RBAC、多租户、消息推送、文件、审计、配置中心、可观测性
- **多端**：Web 管理后台、经销商 Web、场站 Web+大屏、客户端小程序、场站小程序、运维 App、运维 PC

### 2.3 范围外（Out of Scope，v1 不做）

- 预测性维护、AI 客服、智能定价（智能化能力后置）
- 开放平台、V2G、碳足迹、跨境多币种、电池数字护照
- 电网侧调度对接（并网状态仅作字段记录）
- 多租户 SaaS 化对外运营（多租户隔离已启用，但对外自助开通/计费不做）

## 3. 用户角色与权限矩阵

### 3.1 角色清单

| 角色 | 使用端 | 数据范围 | 核心操作 |
|---|---|---|---|
| 平台管理员 | Web 后台 | 全租户 | 用户/角色/组织/租户管理、系统配置、审计查询、模拟他人排障 |
| 平台运营 | Web 后台 | 全部业务数据 | 商品、订单审核、库存、场站、监控大屏、商机跟进 |
| 财务人员 | Web 后台 | 财务域 | 收款确认（对公双人复核）、退款、发票、对账、返利/押金结算 |
| 客服 | Web 后台 | 服务域 | 售后受理、工单协助、客户查询 |
| 场站人员 | 场站 Web + 场站小程序 | 本场站（data_scope 锁定） | 场站监控、告警确认/转工单、工单自领、巡检 |
| 运维工程师 | 运维 App + 运维 PC | 派单区域 | 接单、处理、巡检、扫码查质保、本地诊断、固件烧录 |
| 经销商 | 经销商 Web | 本经销商 | 下单（账期/现结）、我的库存、代客激活/报修、对账、返利查看 |
| 客户（企业/个人） | 客户端小程序 | 本客户 | 设备激活、监控、质保查询、报修、合同查看、商城购物、延保购买 |
| 回收商 | Web 后台（委托登记） | 本回收商相关 | 回收单确认、交接凭证（L3） |
| 设备（系统身份） | IoT 接入层 | 本设备 | 遥测上报、指令 ACK、OTA 进度上报 |

### 3.2 权限模型

- **RBAC 四级**：角色 → 菜单 → 按钮 → 接口。未授权接口返回 403 并记审计。
- **数据权限**：按组织/区域/场站过滤数据集（`data_scope`），同角色不同范围的列表结果不同。
- **敏感操作**：控制类指令（充放电/均衡/保护参数）、退款审核、合同签署等需**二级认证（step-up，5 分钟时效）**+ 全量审计。
- **模拟他人（impersonate）**：管理员可代客户身份排障，全程 `imp_by` 留痕、对被模拟人无感知，仅限授权角色。

## 4. 总体业务流程

### 4.1 设备售卖闭环（模式 B）

```mermaid
sequenceDiagram
    autonumber
    participant C as 客户
    participant O as order
    participant I as inventory
    participant F as finance
    participant CT as contract
    participant D as device

    C->>O: 下单设备（锁定库存）
    O-->>C: 待支付订单（30 分钟超时）
    C->>F: 支付（微信/支付宝/对公）
    F->>O: 支付成功事件
    O->>I: 出库指令（扣减 + stock_record 流水）
    I-->>D: stock_out 事件
    D->>D: 设备状态 = 已出库
    O->>CT: 生成设备合同 + 设备级质保
    CT-->>C: 合同签署（存证）+ 质保凭证
    C->>D: 扫码激活
    D->>D: 绑定客户，质保起算（事件驱动）
```

### 4.2 场站售卖闭环（模式 A）

```mermaid
sequenceDiagram
    autonumber
    participant C as 客户
    participant O as order
    participant S as station
    participant I as inventory
    participant CT as contract
    participant OPS as ops

    C->>O: 下单场站（选模板 + 设备清单）
    O->>I: 锁定场站库存（整体+明细）
    C->>O: 支付成功
    O->>I: 出库（含全部设备）
    O->>S: 创建场站 + 绑定设备清单（Saga 步骤）
    O->>CT: 场站合同 + 场站级质保 + 设备级质保
    S->>OPS: 自动创建场站巡检计划
    Note over S,OPS: 运营期：告警按场站聚合，派单优先场站人员
```

### 4.3 租赁闭环（模式 C，L3）

```mermaid
sequenceDiagram
    autonumber
    participant C as 客户
    participant O as order
    participant CT as contract
    participant F as finance
    participant D as device
    participant OPS as ops

    C->>O: 租赁下单（order.type=LEASE）
    O->>CT: 生成 LEASE 合同（租期/租金计划/押金条款）
    CT->>CT: 签署完成 → 生效（生效才允许出库）
    O->>D: 出库 → 设备状态 RENTED
    F->>F: 押金收取（deposit_account 入账）
    loop 每期账单
        F->>C: 租金账单（逾期自动罚息）
    end
    C->>OPS: 归还申请 → LEASE_RETURN 验收工单
    OPS->>D: 验收通过 → IN_STOCK（或买断转 ACTIVATED）
    F->>F: 押金退还/扣减（三动作台账）
```

### 4.4 告警链路（IoT → 运维闭环）

```mermaid
sequenceDiagram
    autonumber
    participant DV as 设备(BMS/桩)
    participant EMQX as EMQX
    participant ING as iotingest
    participant TS as TDengine
    participant MQ as RocketMQ
    participant OPS as ops
    participant PG as Centrifugo
    participant U as 场站/运维人员

    DV->>EMQX: MQTT/TLS 上报（一机一密）
    EMQX->>ING: 共享订阅转发
    ING->>MQ: 批量投递（背压缓冲）
    MQ->>ING: writer 消费组
    ING->>TS: 批量写遥测（500 条/200ms）
    ING->>MQ: 越限 → alert_candidate
    MQ->>OPS: 告警判定（抑制/级别/场站聚合）
    OPS->>PG: 告警事件推送
    PG-->>U: WebSocket 实时通知（订阅鉴权）
    U->>OPS: 确认 → 转工单（区域+技能派单）
    U->>OPS: 处理 → 提交 → 验收 → 告警关闭归档
```

### 4.5 订阅闭环（模式 D，L3）

订阅计划上架 → 客户开通实例（可绑设备）→ 每月账单周期生成 PENDING 收款单 → 客户 JSAPI 主动支付 → 账单 PAID；额度超量按量计费（口径：场站充电度数，暂人工账单兜底）；退订不满月不折退。自动委托代扣为第二阶段（资质到位后启用，表结构不变）。

## 5. 功能需求（FR）

> 每个域一张表。列：编号 / 需求 / 层级 / 验收要点。

### 5.1 身份与权限（identity，FR-IDN）

| 编号 | 需求 | 层级 | 验收要点 |
|---|---|---|---|
| FR-IDN-001 | 账号管理：手机号/邮箱 + 密码登录，启用/禁用/锁定状态 | L1 | 连续 5 次失败锁定 30 分钟；密码 argon2id 存储；手机号加密存储 + 哈希列保唯一 |

| FR-IDN-006 | 微信登录：code2session + 自动注册 + 手机号绑定（客户端小程序主登录方式） | L1 | 静默续期（checkSession）；首登绑定手机号 |

| NFR-SEC-007 | 按等保 2.0 二级设计（测评上线前执行） | L1 | 预留三级增强项 |
| NFR-SEC-008 | 密钥三件套（RS256/Ed25519/数据密钥）出库管理，种子密码统一环境变量注入 | L1 | 仓库内无任何真实密钥/强密码 |

### 6.5 可观测性（NFR-OBS）

| 编号 | 需求 | 验收要点 |
|---|---|---|
| NFR-OBS-001 | Prometheus + Grafana 指标监控（资源 + RED 业务指标） | 核心服务 RED 全覆盖，看板自动装配 |
| NFR-OBS-002 | 链路追踪：trace_id 贯穿 HTTP→rpc→MQ→消费 | 一次下单可追到库存扣减与事件消费（Jaeger 为主力） |
| NFR-OBS-003 | Loki 集中日志，按 trace_id 聚合检索 | 结构化 JSON 日志，含 trace_id |
| NFR-OBS-004 | 三级告警：资源（CPU/内存/磁盘）、链路（错误率/耗时）、业务（订单失败率/告警积压/DLQ） | 分级触达（电话/短信/企微） |
| NFR-OBS-005 | 新服务上线 DoD：指标注册 + 链路接入 + 健康检查（/healthz /readyz）+ runbook | 静态检查器把关，不满足不允许发布 |

### 6.6 数据一致性（NFR-CNS）

| 编号 | 需求 | 验收要点 |
|---|---|---|
| NFR-CNS-001 | 下单→支付→出库→建站/激活 Saga 编排，失败按补偿表回退 | 补偿动作本身幂等可重试 |
| NFR-CNS-002 | 幂等键三类：saga_id+step / payment_no / event_id 全覆盖 | 重复请求/重放不产生重复副作用（ErrTxnReplay） |
| NFR-CNS-003 | 防超卖：Redis 原子预扣 + DB 行锁双保险；支付超时自动释放 | 并发压测零超卖；Redis 故障降级纯 DB 路径同样安全 |
| NFR-CNS-004 | 事件投递 at-least-once，消费端 event_id 去重表幂等 | MQ 故障恢复补投递不重复消费 |
| NFR-CNS-005 | Outbox 本地消息表：业务事务与事件同库同事务写入，relay 异步投递 | 杜绝"业务成功但事件丢失" |
| NFR-CNS-006 | 兜底对账：库存/资金日结对账，差异生成处理任务 | 差异只允许补投递重放修复 |

### 7.2 数据通用约定

- 全业务表通用字段：`tenant_id`（default 起步）、`created_at/updated_at`、`created_by/updated_by`、`deleted_at` 软删。
- ID：int64 雪花；**对外暴露一律 string**（JS 精度安全）；业务编号带前缀（order_no/station_no 等）。
- 跨服务只存对方 ID（逻辑引用），禁止跨库 JOIN；一致性靠事件 + 对账。
- 一服务一库；每个变更必须有成对的 up/down 迁移脚本。

### 7.3 事件契约需求

- 统一信封：`event_id / tenant_id / trace_id / event_type / occurred_at / payload`。
- **Topic 名下划线**（RocketMQ 命名限制），event_type 保留点号语义名（如 topic `order_created`，event_type `order.created`）。
- 投递 at-least-once；Schema 只增字段向后兼容；大版本变更启用新 Topic。
- 核心事件：order_created / order_paid / order_cancelled / order_pay_timeout（延迟）/ stock_out / stock_low / device_activated / device_status_changed / station_created / iot_telemetry_raw / iot_device_event / alert_candidate / alert_created / ticket_changed / warranty_started / notification_request / audit_event / config_changed / payment_refunded / order_return_approved / cmd_ack / ota_check / report_export_requested 等。

- 同端互斥（QQ 模式）：同 client 登录踢旧，跨 client 共存。
- 前端类型由后端 `.api` 文件自动生成（防手写漂移）。

## 9. 验收标准

### 9.1 通用 DoD（每个功能/服务）

1. 功能用例通过率 ≥ 95%，P0/P1 级缺陷清零；
2. `.api`/proto 接口文件 + 成对迁移脚本 + 单测随代码交付；
3. OpenAPI 文档重新生成且与实现零漂移（CI 阻断）；
4. 多租户审计通过（新表登记 tenant 过滤或豁免）；
5. 可观测 DoD：指标/链路/健康检查/runbook 齐备（静态检查 0 FAIL）；
6. 对应阶段冒烟用例通过（**冒烟严禁并发执行**——共享 FIFO 库存池会交叉消耗造成假失败）。

### 9.2 端到端验收场景

| # | 场景 | 通过标准 |
|---|---|---|
| 1 | 场站订单全流程 | 下单→支付→出库→建站→合同→质保→巡检计划全链路数据一致 |
| 2 | 设备订单全流程 | 下单→支付→出库→激活→告警→工单→关单全链路数据一致 |
| 3 | Saga 补偿演练 | 支付失败自动释放库存；建站失败重试 + 人工介入队列，无残留中间态 |
| 4 | 稳定性压测 | 2,000 台模拟设备连续 72h 上报，零丢失、入库延迟达标 |
| 5 | 故障演练 | 杀 inventory 单实例：下单降级拒绝而非超卖；MQ 积压：恢复后补投递不重复消费 |
| 6 | 安全演练 | 未签名固件下发被拒；越权 WebSocket 订阅被拒；错误设备凭证接入被拒并告警 |
| 7 | 租赁全流程 | LEASE 合同签署→生效→RENTED 出库→归还工单验收→IN_STOCK；押金收/扣/退与收款单对账一致；逾期罚息自动生成 |
| 8 | 多租户隔离 | 租户 A 的订单/租约/告警对租户 B 完全不可见；跨租户 API 直接 403 |
| 9 | 旧数据迁移 | 迁移校验报告差异清零 |
