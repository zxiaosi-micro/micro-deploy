## C · 技术债（登记偿还条件）

> 每条都有"为什么现在能接受"和"什么时候必须还"。

### C1 · 多租户插件的双级租户解析（ambient 机制）

- **现状**：GORM 插件从 `stmt.Context` → 协程级 ambient 两级解析租户。ambient 的存在是因为存量逻辑层大量 `sc.DB.Where(...)` 直查不带 context。
- **为什么能接受**：ambient 在协程创建时绑定、随协程销毁，实测无泄漏；CI tenantaudit 兜底。
- **偿还条件**：逻辑层全部改为 `WithContext` 传入后删除 ambient（预计随"全面 Context 化"重构一起做）；若 Go 标准库提供协程级 context 传播方案则直接替换。

### C2 · RBAC 权限缓存的一致性窗口

- **现状**：权限缓存在 BFF 本地，identity 变更事件主动失效；但事件丢失时最长 30min（access TTL）陈旧。
- **为什么能接受**：权限只升不降的场景（加权限）无风险；降权窗口 ≤30min 且有审计。
- **偿还条件**：出现"降权必须秒级生效"的合规需求时，改为 BFF 每请求查 Redis 的 auth_cache（identity 已有 GetAuthCache 接口，只是当前为性能默认本地缓存）。

### C3 · identity Token 的 key claim 未内置

- **现状**：JWT claims 不含密钥版本 kid（RS256 公钥当前单版本）。
- **偿还条件**：第一次密钥轮换前必须加（轮换时新旧公钥并存需要 kid 路由）——**排进 S11-06 上线门槛**，不能拖到轮换时才想起来。

### C4 · 网关免认证清单是白名单维护

- **现状**：APISIX/BFF 免鉴权路径靠人工清单（登录/回调/webhook 等）。
- **风险**：新增公开接口忘登记 → 上线即 401；或反过来，登记过宽 → 裸奔。
- **偿还**：openapi 工具增加"公开路径与免认证清单 diff 校验"（登记进 03 附录 A 的工具演进）；短期靠 code review  checklist。

### C5 · 前端部分页面未做虚拟滚动

- **现状**：设备列表/流水查询等大数据量表格用 antd Table 常规分页（page_size ≤ 100）。
- **偿还条件**：单页 >1000 行的运营场景出现时上虚拟滚动（或游标分页，02/架构 §7.1 已约定 P4 起大数据量改游标）。

### C6 · 小程序 API 类型仍手写

- **现状**：web 端类型由 apitypes 生成（CI 漂移阻断），小程序端 API 层手写。
- **偿还**：apitypes 扩展 Taro 目标输出（原项目已登记此项）；在此之前小程序字段变更靠 review 自觉。

### C7 · 导出/PDF 渲染同步库较重

- **现状**：XLSX 用 rust_xlsxwriter（desktop）/go 库（analytics），PDF 模板渲染功能较朴素（表格为主）。
- **偿还条件**：出现"复杂版式合同 PDF"需求时引入 HTML→PDF 渲染服务（独立容器，不进业务进程）。

### C8 · 测试对 dev 中间件的部分依赖

- **现状**：testinfra 三级解析让本机有中间件时直接连本机（快），CI 用容器；但少数集成用例（TDengine 路径）在本机无 TDengine 时静默 Skip。
- **风险**：本地一直 Skip 的用例可能悄悄腐烂。
- **偿还**：CI 增加"TDengine service 容器"作业变体强制跑全量；本地跑 CI 同款命令的文档化。

## D · 替代方案与架构演进建议（我的推荐）

> 每条给出：当前方案 → 备选方案 → 我的推荐与理由 → 触发条件。**没有一条是"现在就必须改"**；价值在于当情况变化时，决策依据已经写好。

### D1 · 后端仓库策略：分仓 vs 单仓

- **当前**：5 仓分仓（02 §3，本项目的重建决策）。
- **备选**：①保持单仓（原项目模式）②按域拆 3~4 个服务仓（如 micro-biz / micro-infra / micro-iot）。
- **推荐**：维持 5 仓。**如果团队 ≤4 人或需求以"跨服务联动"为主**（一个需求常改 4+ 服务），单仓更省协调成本——go.work 与 pnpm workspace 都支持随时合并/拆分，**这个决策可逆且成本低**。
- **触发重评**：团队 >10 人、或某域服务需要独立发布节奏与独立权限边界。

### D2 · Saga 编排器：自研状态机 → Temporal

- **当前**：saga 表 + outbox + 延迟消息（ADR-03），单编排流几百行。
- **触发重评**（满足其一）：①编排流 ≥3 条（当前：设备单/场站单/租赁单共享一套状态机，算 1 条主干 + 分支）；②出现多天级人工节点（如建站线下验收走流程）；③需要可视化编排/版本迁移。
- **推荐**：到时迁 Temporal 而非继续加码自研——但**不提前迁**，Temporal 引入的服务端运维与 SDK 学习成本在单流场景是负收益。

### D3 · 检索引擎：MySQL → Elasticsearch

- **当前**：全量 MySQL 检索（ADR-14 两次评估均不引入）。
- **推荐**：维持。备选路径按顺序：①MySQL 全文索引（ngram）覆盖商品/工单模糊搜索；②仍不足再上 ES/OpenSearch（届时只加"检索代理"查询路径，写路径经事件同步，不动主链路）。
- **触发**：核心列表 P95 > 1s 且索引优化到头；或出现真正的全文检索需求（如巡检报告内容搜索）。

### D4 · 时序层：TDengine 单节点 → 集群 / VictoriaMetrics 分工

- **当前**：TDengine 自建容器单节点（遥测）+ Prometheus（监控指标），ADR-013/015。
- **推荐演进**：①3 年目标（2 亿条/日）时 TDengine 扩 3 副本（架构已预留）；②Prometheus 指标保留 >90 天时加 VictoriaMetrics **只做监控指标长期存储**（与业务遥测 TDengine 分工不重叠）；③两者都不合并——"业务遥测"和"监控指标"的查询模式不同，混用一个库反而别扭。

### D5 · 实时推送：Centrifugo → 自研网关

- **当前**：Centrifugo v6 + subscribe proxy 鉴权（ADR-02）。
- **触发重评**：需要推送侧强业务逻辑（动态改写 payload/按用户画像选择性推送/推送侧聚合）时。自研成本 ~2-3 周 + 长期维护；**先做混合**：高频扇出场景（大屏）用 Centrifugo，业务逻辑重的场景降级为轮询 + notification 站内信。

### D6 · 认证：自研会话中心 → Keycloak

- **当前**：自研 sessionx（ADR-11），覆盖互斥/踢人/step-up/SSO 绑定。
- **触发重评**：需要多 IdP 联邦（同时对接钉钉+企微+AD+客户自有 IdP）且角色映射复杂时。Keycloak 学习/定制成本高，**单 IdP 场景自研更轻**——原项目钉钉/企微双 IdP 已验证自研够用。

### D7 · 任务调度：RocketMQ 延迟消息 → asynq / Temporal Schedule

- **当前**：延迟消息（支付超时/工单升级/重试退避）+ 各服务内嵌 cron 扫描（SLA/逾期/巡检）。
- **风险**：cron 扫描散落在多个服务，扫描类逻辑无统一视图。
- **推荐演进**：服务数继续增长时收敛一个 `scheduler` 组件（或 asynq 统一管理周期任务，Redis 已有），**先立"扫描任务注册表"约定**（每个 cron 在 config 服务登记 + 指标暴露 last_run），避免黑盒。

### D8 · iotingest 与 OCPP：协议适配层独立成服务

- **当前**：OCPP 网关是 iotingest 内部模块。
- **触发重评**：接入协议 ≥3 种（MQTT/OCPP/Modbus 边缘网关/厂商私有 TCP）时，拆 `protocol-gateway` 独立部署（每协议一个部署单元，共享"转五指标→MQ"契约）。当前两种协议共享进程可接受（OCPP 连接量小）。

### D9 · 前端微前端化（不建议）

- 明确**不推荐** qiankun/module federation：三端独立部署已解耦，微前端带来的样式隔离/依赖共享问题 > 收益。唯一例外：未来出现"客户在自己系统内嵌我们的设备监控组件"需求，届时做一个**独立 iframe 微应用**（设备监控卡片页）而不是全站微前端。

### D10 · 配置中心演进：yaml+env+config 服务 → Nacos/Apollo

- **当前**（ADR-10）：服务自身配置 yaml+env；业务字典/开关/灰度走 config 服务（版本化+回滚+事件失效）。
- **推荐**：维持。触发重评：多语言服务出现，或配置项规模大到需要权限/审批流。

### D11 · 灰度发布能力补齐

- **现状**：发布为滚动更新 + 健康检查回滚；APISIX 具备按 header/权重的灰度路由能力但未启用业务灰度。
- **建议**：BFF 层启用按用户白名单灰度（新功能先放 5% 内部账号）——APISIX traffic-split 插件配置即可，建议排在多端上线后第一个迭代。

### D12 · 数据血缘与字段级文档自动化

- **建议**：ER 图（01 §7.1 / 03 各阶段）当前人工维护，建议加一个 `ercheck` 工具：解析 migrations 的 CREATE TABLE 自动生成实体清单 + 与 ER 文档 diff（对齐 openapi 漂移检查的思路），**成本 2~3 天，防文档腐烂**。
