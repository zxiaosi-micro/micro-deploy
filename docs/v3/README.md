## v2 → v3 决策变更总表

| # | 讨论点 | v2 口径 | v3 口径 |
|---|---|---|---|
| 1 | **中间件部署形态（新增需求）** | S2-01 本机安装五件套 + compose 起边缘组件 | **全量容器化**：单一全量 compose（profiles：core/edge/obs），不复用、不占用宿主机已有服务；宿主机端口 = 官方默认端口 + 20000（Gotenberg 例外 23001）；有状态数据全部挂卷；密码 `.env` 注入；端口/账号在 compose 注释 + env.md **双登记**。前后端应用服务不容器化，仍本机启动 |
| 2 | **前端合仓名（v2/04 D1 收尾）** | micro-frontend | **micro-web**（合仓策略、目录结构、拆分触发条件全部不变，仅更名） |
| 3 | **可观测六件套去留（v2/04 D4 追问）** | Prometheus/Grafana/Loki/Promtail/Jaeger/Alertmanager 全量常驻 | 建议**方案 A 全保留**：六者各司指标/看板/日志/采集/链路/告警，官方镜像、零代码侵入、合计 ~1GB 量级；dev 用 compose profiles 可选不起 obs。"削 B/C/全去 D"均需连坐修订 NFR-OBS 与 03 阶段验收，不推荐 |
| 4 | **RocketMQ Proxy（v2/03 B6、ADR-12 关联追问）** | 不引入：v2 Go 客户端直连 NameServer | **维持不引入（定稿）**：①Go 侧用 rocketmq-client-go/v2（remoting 协议直连是原生路径），gRPC 版 v5 客户端才是 proxy 的目标用户；②"多语言"需求落在配置中心（Nacos），MQ 事件总线当前是纯 Go 内部链路；③单机 dev 多一容器两端口零收益。触发再评（沿用 B6/ADR-12）：评估 v5 gRPC 客户端/跨语言生产消费、K3s 计算存储分离形态。届时成本极低：broker Local 模式开 `--enable-proxy`，或 Remote 模式加一容器（端口按 +20000 规则 → **28080 gRPC / 28081 remoting**，先登记再起） |

## 连带的结构性变化

| 维度 | v2 | v3 |
|---|---|---|
| dev 中间件 | 本机安装五件套 + compose 起边缘 | **全量 compose**，本机零安装，重启策略 unless-stopped |
| 中间件宿主机端口 | 官方默认端口直用（3306/6379/…） | **默认 + 20000**（22379~38083 号段，Gotenberg 例外 23001）；业务服务端口（8081~8890 / 91xx / OCPP 8182）**不变** |
| envcheck | 探测默认端口 | 探测新端口表（S2-03 随 v3 更新） |
| 仓库名 | micro-frontend | **micro-web**（ADR-17 同步更名，其余 4 仓不变） |
| 环境变量 | — | 新增 `MICRO_DEV_*` 中间件密码组（附录 C 增补） |
| 经验教训 | E1~E15 | 新增 **E16**（端口映射须与 broker listenPort / Nacos gRPC 推导自洽）、**E17**（容器内抓宿主机服务用 host.docker.internal） |
