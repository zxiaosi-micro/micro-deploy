# v3-03 · D4 追问：可观测六件套是什么、要不要、能否去

**版本**：v3.0 ｜ **日期**：2026-10-06
**性质**：v2/04 文档 D4 的展开讨论。**建议方案 A（全保留 + dev 可选启动），待所有者确认**

---

## 1. 先回答 D4 标题里的原命题：TDengine 与监控指标分工

v2/04 D4 的原命题是"**时序层分工**"，v2 已定稿、v3 维持不变：

- **TDengine 存设备遥测**：一设备一子表、降采样保留策略、同 ts 覆盖幂等（业务数据）；
- **Prometheus 存服务运行指标**：QPS/错误率/延迟/资源（运维数据）。两者查询模式不同，**不合并**；Prometheus 指标保留 >90 天时再加 VictoriaMetrics 只做监控长期存储（ADR-15）。

本次追问的是另一半：可观测性那 6 个容器（Prometheus、Grafana、Loki、Promtail、Jaeger、Alertmanager）**分别是干什么的？一定需要吗？是否可以去掉？** 以下逐个拆解。

## 2. 六件套分别是什么——它们不是 6 个独立系统

本质是 **4 类数据（指标/日志/链路/告警）× 各自的采集、存储、展示分工**，互相是上下游：

```
指标：go-zero /metrics(91xx) ──拉取──▶ Prometheus ──PromQL──▶ Grafana 看板
                                          └─告警规则─▶ Alertmanager ─webhook─▶ notification（企微/短信）
日志：*_run.log ──尾随+打标签──▶ Promtail ──▶ Loki ──LogQL──▶ Grafana（按 trace_id 检索）
链路：go-zero otel ──OTLP:24317──▶ Jaeger（trace_id 全链 UI）
```

| 组件 | 一句话角色 | 在本项目具体干什么 | 去掉的直接后果 |
|---|---|---|---|
| **Prometheus** | 指标库 + 告警规则引擎 | 抓 18 个服务 `:91xx`（go-zero 内置暴露，零代码改造）；存 QPS/错误率/P95/资源/MQ 积压/Saga 卡单数；运行三级告警规则 | 服务健康不可见；告警规则无处运行；Grafana 与 Alertmanager 失去数据源（它是整条指标链的地基） |
| **Grafana** | 可视化层 | provisioning 自动装配看板：全局总览 → 服务 RED → 业务指标 → 资源，含轮询接口专项看板（v2 新增）；同时是 Loki/Jaeger 的查询界面 | 只能命令行 PromQL/LogQL 查数；NFR-OBS-001 失去验收载体 |
| **Loki** | 日志库（只索引标签不建全文索引） | 全服务 JSON 日志集中存储；按 trace_id/服务名/级别检索 | 排障退化成逐服务开文件 grep；一次请求跨多个服务的日志串不起来（v2 附录 D 的排障口径失效） |
| **Promtail** | 日志采集 agent | 尾随 `*_run.log`、打标签（服务/环境）推给 Loki | 与 Loki 是一体两面：去它 = Loki 没有数据来源 |
| **Jaeger** | 链路追踪后端 | 收 go-zero otel 上报的 span；UI 按 trace_id 展示一次请求 HTTP→RPC→MQ→消费的完整路径与耗时归因 | Saga 卡单、慢查询、事件链路问题归因黑盒；go-zero 白送的 otel 能力作废 |
| **Alertmanager** | 告警路由 | 接 Prometheus 告警做分组/去重/静默/升级；webhook → notification 出企微/短信 | DLQ 积压、资源告警要么骚扰要么漏报（Prometheus 自带 webhook 无路由静默能力） |

## 3. "一定需要吗"——先看 v2 已经押在它们上面的东西

可观测不是 v2 里孤立的一个选型，它被多处需求与流程引用。去掉哪一块，哪一块的引用就要连坐修订：

| 依赖点 | 内容 | 若去掉受影响 |
|---|---|---|
| NFR-OBS-001~005（v2/01 §6.5） | 指标/链路/日志/三级告警/上线 DoD，全部 L1 | 去哪个改哪个 |
| FR-SYS-004（v2/01 §5.14） | 可观测性基线 L1 | 同上 |
| v2/03 阶段验收 | S3"Grafana 出现 identity RED、Jaeger 可查登录链路"；S6 iotsmoke；S7 轮询接口 RED | 阶段验收需改写 |
| v2/03 附录 D 排障口径 | "服务起不来 → Loki 按 trace_id 搜""带 trace_id 问人（Jaeger:16686）" | 新手排障流程整体退化 |
| v2/03 DoD 静态检查 | dodcheck 校验"指标+链路+健康检查+runbook" | 门槛意义削弱 |

## 4. 成本面——为什么它们"看着多"，实际不重

- 6 个容器**全是官方镜像**，compose 拉起即用，**代码零侵入**（go-zero 内置 Prometheus 指标与 otel 链路，只需配置）；
- dev 合计内存约 **1~1.5GB 量级**（可 mem_limit 压缩）；生产 ECS-2 4C16G 预算内（v2 §12.2 本就含"可观测套件"）;
- 没有"需要人肉运维"的部分：无 schema 演进、无组件间版本联动，挂了重启即可，**数据丢了也不影响业务**；
- 与业务服务**弱耦合**：obs 整组停掉，业务照跑——这正是"可选启动"方案（§5-A）成立的基础。

## 5. 去留方案

| 方案 | 内容 | 省下 | 代价 | 建议 |
|---|---|---|---|---|
| **A · 全保留 + dev 可选启动** | 组件全保留；dev compose 用 profiles 分组，日常可只起 core，排障/验收时 `--profile obs` | dev 内存（obs 不启动时零占用） | 几乎为零；生产维持 v2 口径 | ✅ **推荐** |
| B · 削日志（去 Loki+Promtail） | 日志回退"逐文件 grep" | ~300MB + 2 份配置 | 跨服务排障退化；S11 前要补装；NFR-OBS-003 连坐修订 | 不推荐 |
| C · 再削链路（去 Jaeger） | trace_id 只存在于日志文本中 | 再省 ~200MB | Saga/事件链归因黑盒；S3 阶段验收改写；NFR-OBS-002 连坐修订 | 不推荐 |
| D · 全去 | 只留日志文件 + 人工巡检 | ~1GB | NFR-OBS 五条 + FR-SYS-004 + DoD + 附录 D 全部连坐；18 服务、资金链路、IoT 平台排障裸奔 | ✗ |

## 6. 结论与建议

- **建议方案 A**：把"想去掉"的真实诉求翻译成"**dev 平常不启动**"——落地载体就是 v3-01 的 compose profiles（obs 为可选 profile），能力一个不删，dev 与生产同构可选。
- D4 原命题（TDengine 与监控指标分工、VictoriaMetrics 触发条件）维持 v2 不变。
- **待所有者确认**：确认 A 后结论登记回 v2/04 D 区（D4 补一句"六件套维持，dev profiles 可选启动"）；若选 B/C/D，v3 增量中同步修订 NFR-OBS、FR-SYS-004 与 03 阶段验收条款。
